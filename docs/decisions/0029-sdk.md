# 0029: A Node.js SDK and its docs on the website

- Status: Accepted; webhook verification and pulling added to the SDK ([0040](0040-payment-webhooks-signed-by-secure-cloud.md))
- Date: 2026-11-16

## Context

Apps used the platform through raw HTTP calls to `/v1`. The owner asked for
an SDK simple enough for someone who has just started with Express and
JavaScript, and for its docs on the website. Their choices (2026-11-16):

- the SDK covers **proxy calls, files and user pools** (not flags, secrets
  or the audit log);
- it has **ready-made Express helpers** as well as plain functions;
- it is a **workspace package** in this repository (not published to npm),
  built and tested in CI, and the demo shop uses it;
- the docs are a **/docs section** on the dashboard's site, with a sidebar.

## Decision

- **`packages/sdk` (`@secure-cloud/sdk`)**: TypeScript, compiled to ES
  modules with type declarations; `require()` works too (Node 20.19+ loads
  ES modules with require). No runtime dependencies: Node's own `fetch`,
  `crypto` and streams. Server only.
- **One client:** `new SecureCloud()` reads `SECURE_CLOUD_API_KEY` and
  `SECURE_CLOUD_URL` (default `http://localhost:8080`), so keys stay out of
  code. The key is sent only in the Authorization header; it never appears
  in an error message or when the client is logged.
- **`connections.call(name, "POST /charges", body)`**: JSON by default;
  returns the outside API's answer whatever its status (`ok`, `status`,
  `data`); throws only for the platform's own refusals. A route that could
  leave the connection's base path is refused before any request.
- **`files`**: `upload()` takes a path, a Buffer, a stream, an Express
  request or a multer file, and streams; `list()` reads every page;
  `get()`, `stream()`, `download(id, path)`, `delete()`, `usage()`;
  `send(res, id)` streams a file to an Express response, always as an
  attachment with `nosniff`.
- **`userPool(id)`**: sign up, sign in, refresh, sign out, get a user,
  change a password, and `verify(token)`: the ES256 signature checked
  locally with the pool's public keys (fetched without the API key, cached
  for five minutes), then the audience, token use and expiry.
- **Express helpers:** `requireUser({ cookie })` (bearer header or cookie,
  `req.user`, otherwise a 401) and `errorHandler()`, which answers a user's
  mistakes with their status and message, and setup problems (the platform
  unreachable, or `INVALID_API_KEY`, the SDK's code for the gateway
  refusing the API key) with a plain 500, logged on the server.
- **Errors:** one class, `SecureCloudError` (`status`, `code`, `message`,
  `requestId`), and `isSecureCloudError()`.
- **The demo shop** uses the SDK for files, payments and its shoppers (its
  own fetch code stays for secrets, connections, the audit log and flags).
  Its Docker image builds the SDK first; `syncInjectedDepsAfterScripts`
  keeps the shop's injected copy up to date after `build`.
- **Docs:** `/docs` (public, follows the theme, landingdesign.md's visual
  system): Quickstart (a five minute Express app), Calling outside APIs,
  Files, User sign in, Express helpers, Errors. Copy buttons on every
  example; linked from the landing page, its footer and the dashboard's
  account menu. These are developer docs, which CLAUDE.md now allows next
  to the landing page.
- **Distribution:** `pnpm sdk:pack` writes a tarball to `.local/`;
  developers `npm install` that file. Publishing to npm stays a later,
  manual decision.
- **Tests:** unit tests against a fake gateway (`packages/sdk/test`),
  `tests/e2e/sdk.test.ts` against the running stack, and browser tests for
  the docs (navigation, copy buttons, axe at desktop and phone widths).
  Root `lint`, `typecheck` and `test` build the SDK first.

## Later changes

- Roles and permissions (docs/decisions/0030): `listRoles`, `createRole`,
  `getRole`, `updateRole`, `deleteRole`, `addRole`, `removeRole`,
  `requireRole`, `requirePermission` and `hasPermission`, with a docs page.
- The client looks up the global `fetch` on every call (it kept the first
  one, so tools that replace `fetch` later, like test stubs, were missed).

## Consequences

- CI covers the SDK through the existing root scripts; no new job.
- Not built: flags, secrets and audit in the SDK, retries, other
  languages, an npm release.
