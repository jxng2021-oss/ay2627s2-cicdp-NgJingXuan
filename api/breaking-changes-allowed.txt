# Reviewed exceptions to the breaking-change check (oasdiff --err-ignore).
#
# Breaking changes to the public API are normally refused by CI. Prefer a new
# version (/v2/...) instead. Only if a breaking change is truly intended, and
# every affected client has been told, add it here:
#
#   1. Run `pnpm api:breaking` and copy the reported line, e.g.
#        GET /v1/storage/files/{id} removed the success response with the status '200'
#   2. Paste it below, with a comment above it saying WHY, WHO approved it,
#      and the date.
#   3. The pull request review must cover this file.
#
# Remove entries once the change has reached main; they are not needed again.
#
# 2026-11-05, encrypted storage (docs/decisions/0014), to be approved in the
# PR review by the project owner.
# WHY: files are now encrypted with keys held by the secrets service, so an
# upload or download can't work while it is sealed, and tenants now have a
# storage limit. The two original file routes therefore gained one error code
# each, on statuses they could already return (503 and 413); the shape of
# every response is unchanged. A client that handles "any other code" by its
# HTTP status (as docs/api.md asks) keeps working. All new routes have these
# codes from the start, so only these three lines are needed.
POST /v1/storage/files added the new `SECRETS_SEALED` enum value to the `error/code` response property for the response status `503`
POST /v1/storage/files added the new `STORAGE_QUOTA_EXCEEDED` enum value to the `error/code` response property for the response status `413`
GET /v1/storage/files/{id} added the new `SECRETS_SEALED` enum value to the `error/code` response property for the response status `503`

# 2026-11-12, connection policies (docs/decisions/0019), to be approved in the
# PR review by the project owner.
# WHY: a connection can now have an optional policy. Only connections whose
# owner adds one can ever get the two new codes, each on a status the proxy
# route could already return (403 and 429, same response shape). Existing
# connections have no policy, so nothing changes for current clients; a
# client that handles "any other code" by its HTTP status (as docs/api.md
# asks) keeps working. The new usage route has its codes from the start.

# 2026-11-12, write-only secrets (docs/decisions/0021), to be approved in the
# PR review by the project owner.
# WHY: secret values are no longer readable by anyone: apps use them only
# through proxy connections, which inject them without returning them. This
# GET now returns the version's metadata only. The platform has no external
# clients yet (prototype; the demo shop, the only client, is updated in the
# same change), so this is done as a reviewed exception rather than /v2.
GET /v1/secrets/{name} removed the required property `value` from the response with the `200` status

# 2026-11-24, webhooks (docs/decisions/0040, KAN-145), to be approved in the
# PR review by the project owner.
# WHY: creating, changing and deleting a webhook endpoint are audited like
# proxy connections, so the audit log's action and resource type lists gain
# webhook_endpoint values. Only new values are added to lists that already
# grow with every feature; existing values and the response shape are
# unchanged, and clients reading the log should ignore values they don't know.
GET /v1/audit-events added the new `webhook_endpoint` enum value to the `events/items/resourceType` response property for the response status `200`
GET /v1/audit-events added the new `webhook_endpoint.created` enum value to the `events/items/action` response property for the response status `200`
GET /v1/audit-events added the new `webhook_endpoint.deleted` enum value to the `events/items/action` response property for the response status `200`
GET /v1/audit-events added the new `webhook_endpoint.updated` enum value to the `events/items/action` response property for the response status `200`
